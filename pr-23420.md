## Intent

Reduce Docker image build times in the integration-tests pipeline (DX-4988 target: p50 ≤ 10m). Two levers: raise plugin-build concurrency inside the image builds, and fix the buildkit cache-map so the persistent Go build cache is actually saved and restored across CI runs.

## Big Changes

### Configurable loopinstall concurrency

loopinstall's `--concurrency` flag was hardcoded to 5 in every `install-plugins-*` make target. It is now driven by a new `CL_LOOPINSTALL_CONCURRENCY` make variable (default 5 for local dev), sourced from a new Docker `ARG`/`ENV` pair (`CL_LOOPINSTALL_CONCURRENCY=8`) in `core/chainlink.Dockerfile` and `plugins/chainlink.Dockerfile`, and passed through to each `make install-plugins-*` invocation.

Plugin builds (chainlink-evm, solana, CCIP, etc.) dominate image build time; parallelizing them from 5 to 8 removes their sequentialization as the main bottleneck.

### Fixed Go build cache persistence

`cache-map` handed to `ctf-build-image` was rewritten. The previous entry pointed at an artificial mount target and a source path that did not match where buildkit-cache-dance / actions/cache exchange data; restored cache content never reached the real mount. The map now pins the single cache mount by id (`go-build-cache`) to `/root/.cache/go-build`, the actual GOCACHE location used by every build stage in both Dockerfiles.

The module cache is intentionally excluded — it is large and the "mysterious" upload failures observed in CI come from persisting it.

## Small Changes

* Removed duplicated `--output-installation-artifacts` flags in the output-dir branches of `install-plugins-public/private/testing`; `LOOPINSTALL_*_ARGS` already expands to the same flag+value.
* `CL_LOOPINSTALL_CONCURRENCY` documented inline in the GNUmakefile alongside the other loopinstall knobs.
* Concurrency set to 8 (not higher) in the Dockerfiles to bound peak memory on `ubuntu-latest` runners while several large plugins compile and link simultaneously.

## Callouts

* **Concurrency 8 on `ubuntu-latest`** — check the forced build run on develop for OOM or thrash on cache-miss runs; if headroom is comfortable, raising toward 16 is a cheap follow-up.
* **Cache persistence only exercises on develop pushes** — PR runs skip docker builds when the image exists in ECR (`cache-mode auto` saves only on default-branch runs), so cache restore/save behavior is only observable after merging to develop.
* **Cache identity relies on mount `id`, not target path** — if either Dockerfile's `go-build-cache` mount id changes, the `cache-map` in `integration-tests.yml` must change in lockstep.
* `smartcontractkit/.github` `build-push-docker@v1` interplay: `actions/cache` saves `cache-mount/`, and buildkit-cache-dance treats manual cache-map keys as host paths verbatim, so the map key must stay under `cache-mount/`.
